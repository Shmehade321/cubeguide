# Offline 3×3 Cube Guide — TDD Verification and Delivery Plan

Revision 2 · 20 September 2026

Companion to [the product and technical specification](cube-app-specification.md) and [the implementation contract](cube-app-implementation-plan.md). This document specifies required evidence and delivery gates. It is not a report of product tests already executed.

## 1. What “extensively proven” means here

We can exhaustively test small, finite parts of the engine and mathematically review its invariants. We cannot realistically execute the solver against every one of the roughly 43 quintillion legal states. Even 100% line coverage cannot prove correctness, camera accuracy or usability.

The release claim must be precise: all specified gates passed on named commits, fixtures, hardware and toolchains; every returned solution is checked at runtime; known limits are recorded. Do not use “100% correct for every possible situation” as a test result.

## 2. Mandatory TDD workflow

For each behavior:

1. Link it to a requirement ID and write a focused test with an externally justified expected outcome.
2. Run the test and retain evidence that it fails because the behavior is missing or wrong. A compile failure alone is not the behavioral red phase; add only the minimal declarations needed to get an assertion failure.
3. Implement the smallest complete behavior that passes. Do not use placeholders, constant success responses or mocked solver results in correctness tests.
4. Run the focused tests and the relevant package suite.
5. Refactor with those tests green; run the full PR test plan before claiming the change is complete.
6. Commit a coherent change. Record the requirement, red/green commands and outcomes in the change's verification record.

Write a regression test before fixing every discovered defect. Camera hardware can be replaced at the acquisition boundary for repeatable tests, but the real image pipeline must process actual image fixtures. Solver correctness tests execute the real solver and bundled resources.

Use Swift Testing for unit and integration tests; use XCTest/XCUITest for UI and device-performance tests. Apple documents both frameworks and their roles in [adding tests to an Xcode project](https://developer.apple.com/documentation/xcode/adding-tests-to-your-xcode-project). Simulator workflows using image injection must be labeled as injected-image tests, not live-camera end-to-end validation.

## 3. Independent test evidence

Three representations protect against shared mistakes:

- **Production CubeCore:** explicit 54-position facelet permutations, used for runtime solution replay and canonical application state.
- **Production solver:** separately implemented cubie-coordinate moves and original generated search tables; never generated by calling CubeCore's move function.
- **Test-only oracle:** geometric integer-coordinate rotations of uniquely labeled stickers, authored from face conventions rather than copied production permutations.

Use independently reviewed golden fixtures for each face move and at least one multi-face sequence. Include known physical scrambles and documented facelet snapshots. Solving a scramble generated by the same broken move engine is not sufficient evidence.

Differential solver tests compare legality and solved outcome, not identical solution strings: multiple move sequences can be correct. The pinned upstream reference in the specification is test-only; its timeout/depth failures do not invalidate a legal state. Shared mathematical conventions can still create correlated errors, so add physical golden fixtures and geometric/group checks instead of claiming perfect independence.

## 5. Exhaustive domains

Enumerate manageable domains completely, with fixed expected counts and a check that the runner visited every case:

- 18 face moves × 54 uniquely identified facelets.
- 24 whole-cube orientations and 24 × 18 move-frame transformations.
- All move sequences of length zero through four; deduplicate with the independent test oracle and solve all 46,741 unique states. Exact-distance layer counts are 1, 18, 243, 3,240 and 43,239. A throwaway geometry check in this document review reproduced those counts; the future product suite must reproduce them independently.
- Every single invalid corner twist, edge flip and unmatched piece-pair transposition described in V03; deliberately valid combinations ensure validation is not simply rejecting everything unusual.
- Corner-orientation coordinates (2,187), edge-orientation coordinates (2,048), UD-slice location coordinates (495), 8-piece permutation coordinates (40,320) and 4-piece permutation coordinates (24), when those coordinates are used by the selected solver. These are conventional coordinates described by [Kociemba’s move tables](https://kociemba.org/math/movetables.htm).
- Every entry and legal outgoing move in all six move tables and all four finite abstraction distance tables defined in the implementation contract. Independently rebuild all four distance tables and compare every value. Also check goal distance zero, every neighbor distance difference at most one and a neighbor at distance one less for each non-goal; this catches impossible distances and incorrect goals. No symmetry-reduced domains are used in v1.
- Every documented session state/event pair, including invalid events, through a model-based transition test.

Table validation must check admissibility, not merely hashes. An overestimated pruning bound may discard the only solution path. Cross-check the generator's transitions against the separate geometry oracle; running the same BFS twice over the same wrong transitions would not prove correctness. Hashes only establish that bytes match a known version.

## 6. Randomized and adversarial testing

Use both move-sequence scrambles and directly generated legal cubie states. Random move sequences are not automatically uniform over legal cube states.

For the direct-state generator, select corner/edge permutations with matching parity, choose seven corner orientations and eleven edge orientations, derive the remaining orientation values from the sum constraints, then convert to facelets using a separately tested converter. Review the generator itself and test all its constraints.

Every randomized failure records seed, exact input, generator/version, solver/version, table hashes, limits and platform. Minimize the failure where possible and promote it to a permanent named fixture. A seed alone is insufficient if the generator changes.

Use boundary mutations for malformed inputs and saved sessions. Cap lengths before allocation. Check that invalid input terminates in bounded work rather than hanging or reaching the search engine.

Inject deliberate defects to test test quality: invert a face direction, swap two facelets, remove each parity/orientation guard, corrupt a table entry, ignore an input revision, double-apply acknowledgement, skip replay verification and change a rendering layer axis. Every non-equivalent seeded defect must be detected. Document any equivalent mutation instead of treating it as a missed bug.

## 7. Execution tiers

Counts below are required minimums. They are test budgets, not confidence percentages. Benchmark time before enabling schedules and shard expensive runs without dropping cases. These tiers are project CI requirements; this document review does not create any recurring automation.

| Tier | Required work |
|---|---|
| During each red/green cycle | Focused test, affected deterministic package suite; small fixed regression corpus. |
| Every pull request | All deterministic unit/integration tests; 10,000 seeded legal-state solves; golden image fixtures; guide UI paths; resource integrity; asset/phrase presence; coverage and all changed behavior assertions. |
| Nightly | 100,000 solves with recorded changing seeds; exhaustive shallow states; all compact coordinate transitions; broader image and lifecycle suites; seeded mutation checks. |
| Solver/resource change | Complete shipped-table regeneration and validation; upstream differential corpus; entire mandatory mutation catalog; expanded performance checks. |
| Release candidate | One million legal-state solves; all deterministic regressions; complete asset/audio/visual checks; held-out image evaluation; all specified devices qualified offline; 1,000-state cold and warm benchmarks per device; 20 novice sessions; distribution evidence. |

The one-million-state corpus contains 500,000 directly generated legal states and 500,000 move-sequence scrambles (125,000 each at lengths 20, 40, 80 and 200). Deduplicate by canonical state across both halves and regenerate collisions until one million distinct states exist. Enumerate short/shallow states separately; do not demand hundreds of thousands of unique one-move states. Malformed and known-hard fixtures run in addition. PR/nightly corpora use the same proportions with exact counts recorded.

Maintain named Xcode test plans for PR, nightly and release execution. The pure Swift package runs independently via `swift test`; CI scripts select the relevant corpus by checked-in configuration. T01 maps actual project/scheme names and installed simulator identifiers; it must verify destinations exist and fail rather than silently choose a different platform. No unrun command is a passing result.

## 8. Coverage and skipped-work policy

- Target 100% executable-line coverage for handwritten CubeCore and all explicit validation outcomes. Inspect uncovered lines and branches manually; line coverage is not equivalent to branch coverage.
- Every implemented pruning rule, search exit, resource failure and cancellation point has a targeted test. Solver internals also need differential and property checks; line percentages alone are insufficient.
- Generated data and external code are inventoried separately, with their own asset and behavioral verification. Do not inflate coverage by excluding handwritten risky code.
- No production `fatalError` placeholders, stubbed success paths, known ignored edge cases, disabled correctness tests or accidental test discovery gaps.
- Every required test plan records discovered/run/skipped counts. Unexpected skips, runner crashes and missing device evidence are failures of the release gate.
- UI visuals and physical handling require visual/human checks even when state tests pass. Record them explicitly instead of calling them automated coverage.

## 9. Camera dataset and human verification

Create a labeled corpus of at least 300 complete capture sessions (1,800 face images): 100 for development/calibration and 200 held out. Keep captures from the same cube/lighting session in one partition; include held-out cube units and environments. Verify each ground-truth sticker manually and independently replay any scramble used to create the state.

Cover stickered/stickerless finishes, warm/cool lighting, indirect daylight, small angular offsets, wear and multiple devices. Maintain additional stress captures for glare, darkness, occlusion and unreadable stickers. Stress cases must produce correction/retry or accurate acceptance; rejection alone cannot satisfy the ordinary-lighting usability target.

Track per-sticker, whole-face and whole-cube accuracy, correction count, false confident acceptance, retry count and time to complete capture. Whole-cube accuracy is the product-relevant metric. Image fixtures test algorithms; repeated physical sessions test focus/exposure behavior and whether users follow orientation instructions.

Each of the 20 novice trials starts with a physical scramble and ends with inspection of all six physical faces. Include wrong-turn recovery, pause/resume and at least one denied-camera/manual-entry trial in the total qualification program. Record baseline cube, device/OS, outcome and assistance given; do not save identifying participant images as product telemetry.

## 10. Delivery milestones

T01–T12 in the companion implementation contract define the work within these milestones. Every behavior follows section 2; a milestone is not one giant test-first change.

| M4 — 3D guidance | Matching scene, icons, highlighted turns/regrips, narration/effects/haptics, acknowledgement, replay, mismatch recovery and persistence | V09–V11, V13 and V14 pass for implemented screens/assets; all transforms checked; no drift or duplicate advancement. |
| M5 — Guided camera scan | Six-face capture, traditional color recognition, corrections and scan-to-solver integration | V07–V08 pass; held-out accuracy and recovery goals reached; physical capture evidence recorded. |

M0–M2 establish correctness before camera and rendering complexity. M3 provides an independently usable fallback. M4 and M5 add user-facing complexity with the verified engine already available.

## 11. Required release evidence bundle

Store the source commit, Xcode/Swift versions, dependency revisions/licenses, resource/generator hashes, test-plan versions, test result bundles, coverage reports, randomized corpus manifests/seeds, mutation report, image confusion/error report, device performance measurements, offline checks and physical usability results.

For every R01–R20 requirement, list its implementing task/milestone, automated suite, physical checks where applicable and current pass/fail status. An evidence record that says “not run” cannot be summarized as “passed”.

Do not claim the app or algorithms have been tested from the existence of this document. Implementation needs the actual repository; physical/media/distribution evidence needs the inputs listed in specification section 15.

## 13. Evidence rules for media, CI and qualification

- Media TDD starts with a failing manifest/mapping test before wiring the feature. A file being decodable cannot prove narration says the correct words; every recording needs a listening sign-off against its caption. Visual snapshots need human review; never auto-update all baselines after a failure.
- Test stale callbacks from audio, camera, file writes, animation and solver jobs after reset/delete/background. A cancelled job cannot resurrect deleted state or play old instructions. Failed persistence callbacks cannot advance a replacement session.
- Test deletion during an outstanding save by serializing/cancelling writes and using a deletion generation; after completion, no late write may recreate the old data.
- Asset lint enumerates all A/N/E IDs and checks production bundle membership, source/rights records, empty files, invalid codec/image dimensions and missing dark/tinted icon configuration when required by the chosen asset format. No unused placeholder is a release asset.
- Run leak checks and race/thread diagnostics in dedicated debug jobs; run timing/memory gates in optimized Release without sanitizers. Test Swift strict concurrency checking. Do not compare debug/simulator performance with Release/device budgets.
- Record device model, OS build, power mode, battery/thermal status, app build, test corpus, table version, repetitions and raw durations. Cold means a fresh process with unloaded tables; warm means preloaded verified tables. Use nearest-rank percentile on all 1,000 outcomes, count timeouts as misses, and report maximum; do not discard slow outliers. Reboot/first-install tests are additional cases, not every cold sample.
- The release evidence manifest has fields: requirementID, testIDs, commit, build, resourceHashes, environment, startedAt, finishedAt, result, evidencePaths, owner, and blockerReason if not passed. Allowed results: notRun, running, passed, failed, blocked. Completed subsets cannot imply the entire release passed.
- PR checks may run a finite subset; the candidate must run the full release tier. Unrelated fixture/tooling failures still appear in the report; no automatic retries that hide flaky failures. A flaky required test is a defect to diagnose.
- A late source/asset/resource change invalidates affected unit/integration/media/device evidence and the candidate archive. Rerun the affected suites plus PR regression; rebuild/distribute and re-run offline/archive integrity checks. Algorithm/table changes also rerun full solver qualification. Preserve unaffected historical evidence with a written impact assessment.
- Submission assets and actual release checks require live owner inputs. Agents must continue independent work while reporting those gaps; they must not fabricate a privacy URL, signing identity, physical test or App Store approval.
